- 한글 조합 중 `⌘A`: 조합을 먼저 확정한 뒤 선택·편집 명령을 처리하도록 수정했다. 전체 선택, 방향키, 삭제, 붙여넣기, 줄바꿈, Tab 회귀 테스트가 통과한다.

- 화면 의존 배율 테스트: 100% 미만이라는 가정 대신 실제 페이지가 viewport에 들어오는지를 확인한다.
- 최종 `make test`: Rust 48개 통과(선택 실행 2개 제외), Swift 46개 통과(선택 실행 2개 제외).
- 실제 macOS 한글 입력기와 최신 앱을 이용한 수동 확인은 다음 실행 점검 때 한 번 더 수행한다.

## 먼저 알아야 할 것

- 현재 소스에는 본문 그림 선택, 이동, 8방향 크기 조절, `Delete`/`Backspace` 삭제, 개체 속성, 본문 배치 방식 변경 기능이 들어 있다.
- 그런데 확인 당시 실행 중이던 앱은 현재 소스보다 오래된 빌드였다. 소스 HEAD 시각은 17:25였지만 실행 파일은 12:46에 만들어져 있었다. 그래서 “이미지 크기 조절·삭제가 없다”는 화면은 최신 소스의 동작이 아니었다.
- 엔진을 다시 만들기 전 `swift test`에서는 새 Swift 코드와 오래된 Rust 엔진의 ABI가 맞지 않아 17개 문제가 났다. `make engine` 후에는 36개 테스트 중 화면 자동 맞춤 배율 테스트 1개만 실패했고, 선택 실행 테스트 2개는 건너뛰었다.
- 따라서 pull 뒤에는 반드시 엔진과 앱을 함께 새로 만들어야 한다. 단순 `swift test`만으로는 최신 상태 검증이 되지 않는다.

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer make engine
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer make run
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer make test
```

## 1. 입력 직후 저장 시 마지막 편집 유실 — P0

### 재현

1. 빈 문서에 `저장 직전 입력`을 입력한다.
2. 이벤트 루프가 한 번 돌기 전에 바로 HWPX 스냅샷을 만든다.
3. 저장 결과를 다시 연다.
4. 기대값은 `저장 직전 입력`이지만 실제 결과는 빈 문자열이다.

### 원인

`HwpDocument`의 편집 명령은 MainActor의 `Task`에서 나중에 엔진 큐로 전달된다. 반면 `snapshot(contentType:)`은 대기 중인 문서 편집이 엔진 큐에 들어왔는지 확인하지 않고 바로 `session.export`를 호출한다. `EditSession.export`가 자체 큐를 비워도, 아직 `HwpDocument`의 Task 안에 남은 요청까지 기다릴 수는 없다.

관련 코드:

- `App/Document/HwpDocument.swift`의 `snapshot(contentType:)`
- 같은 파일의 `enqueue`
- `App/Editing/EditSession.swift`의 export 경로

### 수정 방향

- 수동 저장, 자동 저장, 창 닫기 저장이 모두 같은 “편집 반영 완료 후 내보내기” 경로를 사용하게 한다.
- MainActor에서 Task 완료를 동기 대기하면 교착될 수 있으므로 피한다.
- 가능한 방향은 NSDocument 비동기 저장 흐름에서 `settle`을 await하거나, 편집 요청을 생성 시점에 곧바로 순서 보장 큐에 제출해 snapshot이 반드시 뒤에 서게 만드는 것이다.
- 저장 실패는 경고음이 아니라 사용자에게 원인과 복구 방법을 보여줘야 한다.

### 완료 조건

- 입력, 글자 모양 변경, 그림 이동·크기 변경 직후 각각 즉시 저장해도 다시 열었을 때 그대로다.
- HWP와 HWPX 양쪽에서 확인한다.
- 자동 저장 및 창 닫기 저장에도 같은 회귀 테스트가 있다.

## 2. 한글 조합 중 전체 선택 후 입력이 전체를 교체하지 않음 — P0

### 재현

1. 한글 입력기로 `안녕하세요`를 입력하되 마지막 글자가 아직 조합 중인 상태를 만든다.
2. `⌘A`로 전체 선택한다.
3. `반갑습니다`를 입력한다.
4. 기대값은 `반갑습니다` 하나지만, 실제로는 이전 문자열 일부가 남은 채 뒤쪽만 바뀐다. 진단 테스트에서는 `안녕하세반갑습니다`가 됐다.

### 원인

`PageEditor.selectAll`은 선택 범위를 바꾸지만 진행 중인 IME 조합을 확정하지 않는다. 다음 `insertText`가 들어오면 남아 있는 `markedText`와 `HwpDocument.marked`를 보고 전체 선택 대신 예전 조합 범위를 교체한다.

추가로 `NSTextInputClient.selectedRange()`가 실제 선택을 충분히 반영하지 않고, 입력기의 `replacementRange`도 무시되고 있어 IME 계약이 약하다.

관련 코드:

- `App/Workspace/DocumentCanvas.swift`의 `selectAll`, `insertText`, `setMarkedText`, `selectedRange`
- `App/Document/HwpDocument.swift`의 `compose`, marked range 관리

### 수정 방향

- 선택 또는 편집 대상을 바꾸는 명령 앞에서 조합을 한 곳에서 일관되게 확정한다.
- 적용 범위: `⌘A`, 방향키·Home/End 이동, 마우스 선택, 붙여넣기, 삭제, Enter, Tab, 찾기 결과 이동, 포커스 이동.
- 조합 확정과 새 입력이 사용자 입장에서 한 번의 자연스러운 undo가 되도록 한다.
- `replacementRange` 및 `selectedRange()`를 AppKit 입력기 계약에 맞게 구현한다.

### 완료 조건

- 실제 macOS 두벌식 입력기로 위 시나리오가 정상 동작한다.
- 조합 중 `⌘A` 후 입력·붙여넣기·삭제, 방향키 이동 후 입력, Enter/Tab을 회귀 테스트로 고정한다.
- 영문과 일반 선택 교체 동작도 깨지지 않는다.

## 3. 오래된 엔진·앱 산출물 혼용 — P0 개발 흐름

### 증상

- pull한 최신 코드에는 그림 도구가 있는데 실행 앱에서는 보이지 않는다.
- 엔진 프로토콜이나 명령이 추가된 뒤 Swift 테스트만 실행하면 오래된 dylib와 연결되어 무관해 보이는 다수 테스트가 실패한다.

### 원인

생성된 엔진과 앱이 소스 커밋 또는 프로토콜 버전과 일치하는지 시작 시 검증하지 않는다. 현재 생성 폴더는 Git에 추적되지 않아 pull이 성공해도 로컬 산출물은 그대로 남는다.

### 수정 방향

- 편집 프로토콜에 ABI/schema 버전을 두고 Swift와 Rust가 시작 시 서로 확인한다.
- 앱 정보 화면 또는 진단 로그에 Git 커밋과 엔진 버전을 표시한다.
- 불일치 시 조용히 실행하지 말고 “엔진을 다시 빌드해야 함”을 명확히 표시한다.
- CI는 깨끗한 checkout에서 `make test`를 실행해 엔진 생성부터 검증한다.
- README의 pull 후 실행 절차를 `make engine` → `make run`으로 통일한다.

### 완료 조건

- 이전 엔진을 일부러 둔 상태에서 최신 앱을 실행하면 즉시 이해 가능한 오류가 나온다.
- 깨끗한 checkout의 CI에서 전체 빌드와 테스트가 통과한다.

## 4. 그림 편집 기능의 현재 상태와 남은 문제

### 최신 소스에 이미 있는 기능

- 본문 그림 클릭 선택
- 8개 조절점으로 크기 변경
- 드래그 이동
- `Delete`/`Backspace` 삭제
- 빠른 메뉴와 개체 속성
- 글자처럼 취급, 사각형 배치, 글 위·아래만 배치, 글 뒤, 글 앞
- 자르기, 여백, 밝기·대비·효과, 캡션
- undo와 저장 관련 기본 테스트

주요 구현 위치:

- `App/Workspace/DocumentCanvas.swift`
- `App/Workspace/ObjectSheets.swift`
- `Engine/crates/hwp-engine-abi/src/editing/objects.rs`

### 4-1. 표 셀 등의 그림은 지원 범위 밖 — P1

Rust 개체 열거는 `cellIdx`, `cellPath`, `noteRef`, `headerFooter`가 있는 개체를 제외한다. Swift 그림 삽입도 선택 위치가 표 셀이면 거부한다. 따라서 학교 양식에서 자주 필요한 “표 칸 안에 사진 넣기·선택·조절·삭제”가 현재는 불가능하다.

수정 방향:

- `ObjectRef`가 본문 문단 번호만이 아니라 셀 경로, 글상자, 각주·미주, 머리말·꼬리말의 위치를 표현하도록 확장한다.
- hit test, 선택 표시, 이동·크기 조절, 삭제, 저장, undo가 동일한 경로 식별자를 사용하게 한다.
- 가장 먼저 표 셀 안 그림 삽입·선택·크기 조절·삭제를 end-to-end 테스트한다.

### 4-2. `크기 고정`을 조절점이 무시 — P1

개체 속성 창에는 `sizeProtect`가 있지만 캔버스는 개체 종류만 보고 조절점을 표시하며, 드래그가 끝나면 폭과 높이를 그대로 기록한다.

수정 방향:

- 배치된 개체 정보에 `sizeProtect`를 포함한다.
- 고정 개체에는 조절점을 숨기거나 비활성화하고 드래그 명령도 엔진에서 거부한다.
- UI뿐 아니라 엔진에서도 보호 속성을 검증해 다른 호출 경로로 우회되지 않게 한다.

### 4-3. 그림 비율 유지 기본값 — P3/정책 결정

현재는 Shift를 누른 모서리 드래그에서만 비율을 유지한다. 사진은 기본적으로 비율을 유지하고 보조키로 자유 변형하는 방식이 더 안전할 수 있다. macOS 사용 감각과 한컴 동작 중 어느 쪽을 따를지 결정한 뒤 테스트한다.

## 5. 비동기 잘라내기 경합 — P1

`cut`은 처음 선택한 범위의 텍스트를 비동기로 읽은 뒤, 완료 시점의 현재 선택에 `replaceSelection(with: "")`을 실행한다. 읽는 동안 사용자가 선택을 바꾸면 복사한 범위와 삭제한 범위가 달라질 수 있다.

수정 방향:

- 처음 캡처한 정확한 범위에 대해 읽기와 삭제를 하나의 직렬 명령 또는 트랜잭션으로 실행한다.
- 최소한 완료 시 선택이 캡처값과 같은지 확인하고, 다르면 삭제하지 않는다.
- 지연을 강제로 넣은 테스트에서 선택 변경 시 엉뚱한 텍스트가 지워지지 않아야 한다.

관련 코드: `App/Workspace/DocumentCanvas.swift`의 `cut`.

## 6. 편집 오류가 경고음으로만 사라짐 — P1

`HwpDocument.enqueue`를 비롯한 여러 편집·그림·속성 경로가 `catch` 또는 `try?` 뒤 `NSSound.beep()`만 호출한다. 문서 잠김, 미지원 기능, 저장 실패 등 과제 파일에 치명적인 상황에서도 사용자는 무엇이 실패했는지 알 수 없다.

수정 방향:

- 사용자에게 보여줄 typed error 상태를 문서 단위로 둔다.
- 복구 가능한 오류는 배너/시트로 원인과 다음 행동을 안내한다.
- `.locked` 상태에서는 편집 UI를 선제적으로 비활성화한다.
- 문서 본문 내용은 남기지 않는 범위에서 OSLog에 명령 종류, 엔진 코드, 파일 형식, 버전을 기록한다.
- 실패 경로를 테스트에서 관찰할 수 있게 한다.

## 7. 찾기 창 포커스 실패 가능성 — P1, 최신 빌드 재확인 필요

이전 실행 앱에서는 캔버스에서 `⌘F`를 누른 뒤 입력한 `abc`가 검색창이 아니라 도구 막대의 글자 크기 칸으로 들어갔다. 현재 소스는 `FindBar`의 `.onAppear`와 `.onChange`에서 focus를 요청하지만 명시적인 AppKit responder 이관이 없어 같은 문제가 남았을 수 있다.

수정 방향:

- 최신 앱을 완전히 다시 만든 뒤 먼저 재현 여부를 확인한다.
- FocusState를 단일 enum으로 관리하거나 AppKit responder bridge를 사용해 다음 run loop에서 검색 필드를 확실히 first responder로 만든다.
- 캔버스 및 도구 막대 입력칸에서 각각 `⌘F`를 시작하는 UI 테스트를 추가한다.
- 찾기 창을 닫으면 이전 편집 위치로 포커스가 돌아가야 한다.

관련 코드: `App/Workspace/DocumentWindow.swift`의 `FindBar`.

## 8. 컨테이너를 넘는 선택 — P2

엔진의 선택 정렬 키는 문단 번호와 글자 위치만 사용하고, 본문·셀·각주 등 서로 다른 컨테이너를 한 선택으로 편집하는 것을 거부한다. UI에서 드래그가 경계를 넘어가면 선택 표시가 사라지거나 편집이 경고음으로 끝날 수 있다.

단기 수정은 드래그 선택을 현재 컨테이너 경계에서 멈추는 것이다. 장기적으로는 한컴처럼 구조화된 다중 컨테이너 선택을 지원할지 결정한다. 본문↔표, 셀↔셀 경계를 테스트한다.

관련 코드: `Engine/crates/hwp-engine-abi/src/editing/commands.rs`.

## 9. 빠른 검색어 변경 시 결과 역전 가능성 — P2

검색 작업은 await 후 공유 `matches`에 결과를 쓴다. `.task(id:)`가 바뀌어도 이미 엔진에 들어간 작업이 완전히 취소되지 않으면 오래된 검색어의 결과가 새 검색어 결과를 덮어쓸 수 있다.

수정 방향:

- 요청 시작 시 query와 문서 revision을 캡처한다.
- await 뒤 현재 query/revision 및 취소 상태가 동일할 때만 결과를 반영한다.
- 일부러 응답 순서를 뒤집은 테스트를 추가한다.

관련 코드: `App/Workspace/DocumentWindow.swift`의 검색 작업.

## 10. 복합 문자 shaping 우회 위험 — P2, fixture 필요

`PageDisplay`에는 Unicode scalar 수와 UTF-16 길이가 같으면 글리프를 직접 매핑하는 빠른 경로가 있다. 결합 문자, 옛한글 자모, 아랍어 중 일부는 이 조건을 만족해도 문맥 shaping이 필요하므로 글자 뭉개짐이나 위치 오류가 날 수 있다.

수정 방향:

- 빠른 경로를 shaping이 불필요하다고 보장되는 문자로만 제한하거나 모든 복합 run을 CoreText typesetter로 보낸다.
- 현대 한글, 옛한글 자모, 결합 악센트, 아랍어, emoji ZWJ fixture를 만든다.
- 화면과 PDF 양쪽을 기준 렌더와 비교한다.

관련 코드: `App/Editing/PageDisplay.swift`.

## 11. 자동 맞춤 배율 테스트가 화면 환경에 의존 — 테스트 수정

최신 엔진 재빌드 후 전체 Swift 테스트의 유일한 실패는 `DocumentTests.canvasDrawsPagesAndCaret`의 `canvas.zoom < 1`이었다. 실제 값은 약 `1.026`이었다. 창 크기에 따라 페이지를 맞추기 위해 100%보다 조금 확대하는 동작은 정상일 수 있으므로 제품 버그라기보다 오래된 단정에 가깝다.

수정 방향:

- `zoom < 1` 대신 fit 모드 여부, 유한한 양수 배율, 페이지가 viewport 안에 들어오는지를 검증한다.
- 또는 테스트 viewport 크기를 고정해 화면·모니터에 독립적으로 만든다.

## 진단 시점의 테스트 기준선

- Rust 엔진 재빌드: 성공(상위 rhwp 코드의 deprecated 경고 1건)
- Swift 테스트: 총 36개 중 1개 실패, 2개 opt-in 테스트 건너뜀
- 실패: `DocumentTests.canvasDrawsPagesAndCaret`의 화면 의존 배율 단정
- 엔진 재빌드 전: 오래된 ABI 때문에 17개 문제 발생
- 이 문서를 만들기 위해 임시로 추가했던 재현 테스트는 진단 후 제거했으며, 제품 코드는 변경하지 않았다.

현재 기준선은 위의 P0 안정화 결과를 따른다. 이전 수치는 최초 원인을 추적할 때의 기록으로 남겨 둔다.
