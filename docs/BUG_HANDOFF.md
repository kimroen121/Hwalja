# 남은 버그와 점검

기준: `make test` 통과. 앱을 바꾼 뒤에는 `make engine`과 `make run`으로 엔진과 앱을 함께 다시 만든다. 편집 실패는 경고음으로 알린다(결정됨).

## 위치 규칙

엔진과 앱의 위치(`scalar`)는 글자 하나, 그리고 줄 안에 놓인 개체(글자처럼 취급 그림·수식·표·그리기 개체, 각주·미주 번호) 하나를 각각 한 칸으로 센다. rhwp의 본문 커서 함수가 이렇게 센다. 앱이 받는 문단 글자에는 개체 자리마다 U+FFFC가 들어 있고, 복사할 때는 빠진다. rhwp의 글자 편집 함수는 글자만 세므로 엔진(`editing/logical.rs`)이 바꿔 넘긴다. rhwp의 클릭·줄·선택 영역·칸 커서 함수는 개체 다음 줄부터(칸에서는 더) 위치를 다르게 세므로, 줄 안 개체가 있는 문단은 엔진이 쪽 배치(`get_page_text_layout_native`, `get_page_control_layout_native`)로 멈춤점을 직접 만들어 쓴다(`editing/stops.rs`, 수정 번호별 캐시). 실제 문서 47개에서 커서→클릭 왕복이 같은 문단 안에서 어긋난 것은 13,039곳 중 15곳(개체 없는 문단 27,583곳 중 20곳과 같은 수준).

## 수동 점검 (자동화하지 못함)

화면이 꺼진 환경에서는 `screencapture`가 검은 화면만 찍으므로 앱 테스트의 스냅샷(`HWP_SNAPSHOT_DIR`)으로 대신 본다. 아래는 실제 창에서 손으로 확인해야 하는 것이다.

### 편집
- [ ] 서식 있는 복사·붙이기를 Pages와 주고받기: Pages가 설치돼 있지 않아 RTF(텍스트 편집기와 같은 형식)로만 확인함.

### 머리말·꼬리말
- [ ] 보호 필드: 쪽 번호·파일 이름 필드를 포함해 전체 선택 후 입력하거나 오려 두었을 때 필드는 남고 일반 글자만 바뀌는지(한컴 문서로). 앱이 넣은 쪽 번호는 필드가 아니라 지워지는 조판 부호임.

### 파일
- [ ] 암호가 걸린 문서: 앱의 암호 창에서 취소하면 오류 창 없이 닫히는지, 저장한 파일을 한글에서 암호 1234로 여는지. 잠금 아이콘·파일 이름·입력란, 틀린 암호에 다시 묻기, 저장한 파일을 한컴 뷰어가 암호로 묻는 것까지는 확인함(`Tests/Fixtures/locked.hwp`).

## 남은 문제

순위: P1 내용이 틀리거나 잃을 수 있음, P2 눈에 띄게 다름, P3 드묾·사소함.

### 조판 (rhwp)

| 순위 | 문제 | 메모 |
|---|---|---|
| P2 | 줄 정보 없는 문서의 쪽 나눔이 한 줄 다름 | 문단 분할 때 4px 안전 여백을 두 번 빼던 것은 수정·회귀 테스트함. 미적분 보고서 2→3쪽의 문단 26은 여전히 7줄/4줄이라 한컴 기준 줄 배분 재확인 필요 |
| P2 | 본문 아래로 넘치는 줄·표 | 로컬 문서 여럿에서 rhwp가 `LAYOUT_OVERFLOW`를 내며 본문 밖(최대 수백 px)에 그림. 쪽 윤곽을 끄면 본문 영역으로 잘리므로 넘친 부분이 안 보임. 쪽 나눔에서 표·문단 높이를 바로잡아야 함 |
| P2 | 띄어쓰기가 넓어 보임 | 엔진(rhwp)이 한컴 규약대로 공백을 글자 크기의 절반으로 잡음(함초롬바탕 실제 공백은 0.3em). 줄 나눔이 한컴과 달라지므로 바꾸지 않았음. 보기 전용 조정이 필요하면 결정 필요 |
| P2 | 고친 머리말·꼬리말의 양쪽 정렬 한 줄이 영역 끝까지 벌어짐 | 앱에서 만든 머리말에 `학교 머리말`을 쓰면 두 낱말이 양 끝으로 갈라짐. 같은 파일을 한컴 뷰어는 벌리지 않음. rhwp가 저장된 줄 정보(LINE_SEG)가 있는 머리말·꼬리말의 마지막 줄을 공백에 나눠 벌리는데(#1692·#4516, 한컴 원본을 따른다고 함), 고친 문단의 줄 정보도 저장된 것으로 셈. 그 규칙이 맞는 한컴 원본 표본으로 범위를 확인해야 함 |
| P3 | 테스트용으로 만든 hwp 문서에 그림을 넣으면 쪽이 늘어남 | 실제 문서 47개에서는 생기지 않음(rhwp 생성 hwp의 줄 정보 문제로 보임) |

### 편집

| 순위 | 문제 | 메모 |
|---|---|---|
| P1 | 문단 번호 모양의 「새 번호 목록 시작」이 저장되지 않음 | 화면에서는 시작 번호대로 매겨지나 hwp로 저장하면 사라짐(한컴 뷰어에서도 앞 번호에 이어짐). rhwp는 `numbering_restart`를 메모리에만 두고 읽지도 쓰지도 않음. 한컴이 이를 HWP·HWPX에 어떻게 적는지(새 문단 번호 정의 등) 한컴 표본으로 확인한 뒤 쓰기를 더해야 함 |
| P3 | 쪽 번호만 있는 머리말의 공백 한 칸이 문서 통계 글자 수에 들어감 | 한컴 뷰어보다 한 자 많음(30 대 31). 앱이 넣은 쪽 번호 머리말 문단의 글자가 공백 하나임 |
| P3 | 서로 다른 컨테이너를 넘는 선택 | 끌어 선택은 경계에서 멈춤 |

## 내부 개선

### 성능
- [ ] 남은 엔진 시간(키 입력 한 번에 약 20ms): 편집 쪽과 다음 쪽의 SVG(레이아웃 포함), 표시 목록의 XML 파싱. 다음 후보는 rhwp 렌더 트리(`get_page_layer_tree_native`)에서 표시 목록을 바로 만드는 것(SVG 문자열과 XML 파싱 생략).
- 측정: 엔진 `HWP_BENCH=<문서> cargo test --release bench_typing -- --ignored --nocapture`, 앱 `HWP_BENCH=<문서> swift test -c release --filter benchHostedTyping`.

### 개발 도구
- [ ] 저장소 루트의 `cargo fmt --manifest-path Engine/Cargo.toml --all -- --check`가 생성된 `build/rhwp`까지 검사하다 없는 테스트 target 때문에 실패함. 추적 소스만 보는 `make fmt-check`를 두거나 생성 엔진을 포맷 대상에서 빼야 함. 지금은 `Engine/`에서 `cargo fmt`를 돌리고 `git diff --check`로 확인.

### 한컴과 비교
- [ ] 서식의 한컴 시각 일치: 진하게는 화면 표시용 face가 bold로 바뀌는 것까지 테스트함. 기울임·밑줄·취소선·글자 크기·색·형광펜, 글자·문단 테두리와 배경은 HWP/HWPX 저장 후 한컴 PDF와 비교해야 함(저장·다시 읽기는 테스트함).
- [ ] 비교 도구: 한컴 뷰어에서 PDF로 인쇄한 결과와 쪽마다 픽셀 비교. 지금은 손으로 나란히 본다: 엔진 `HWP_RENDER=<문서> HWP_RENDER_DIR=<폴더> cargo test render_pages -- --ignored`(쪽 SVG·PDF), 앱 `HWP_SNAPSHOT_DIR=<폴더> HWP_SNAPSHOT_DOC=<문서> swift test --filter snapshots`(캔버스 그대로의 쪽 PNG, 쪽 윤곽 끈 모습 `draft.png`).
