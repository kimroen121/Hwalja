# HwpStudio 로드맵

목표: HWP/HWPX 문서를 원본 훼손 없이 편집하는 macOS 네이티브 편집기.

- 1차 기능 목표: 한컴오피스 Web 한글(웹 편집기)의 기능을 최대한 구현한다.
- 2차 기능 목표: 로컬 한글(데스크톱) 수준까지 끌어올린다.
- 화면 기준: 조판 결과는 로컬 「Hancom Office HWP Viewer」와 최대한 같게 한다. UI는 Apple HIG를 따르고, 앱 안에 설명 문구를 넣지 않는다.

원래 설계(2026-10-04 「텍스트 편집 1단계」 spec/plan)의 원칙을 이어 가되, 순서를 조정했다.
문서 전체를 PDF로 다시 만드는 방식은 키 입력 속도를 견디지 못하므로 쪽 단위 렌더링을 앞당겼다(완료).
rhwp에 저장 API가 있으므로 저장도 마지막까지 미루지 않았다.

## 지켜야 할 원칙

- 원본 파일에는 명시적인 「저장」 전까지 쓰지 않는다. 저장은 원자적으로 하고, 저장 전에 재파싱으로 검증한다.
- 화면과 내보내기는 같은 조판 결과를 쓴다.
- 안전성을 확인할 수 없는 대상(필드·제목 표시가 있는 문단, 세로쓰기 셀, 중첩 표, 머리말·꼬리말 안의 글자)은 읽기 전용으로 둔다. 숨은 컨트롤을 평문으로 바꾸지 않는다.
- 조합 중인 글자는 문서에 바로 넣어 문서 글꼴로 보인다. 조합 하나, 붙여넣기, Enter 각각이 실행 취소 1단위다. 엔진이 앞 편집을 처리하는 동안 이어 친 글자는 한 편집(1단위)으로 묶인다. Undo/Redo는 내용·커서·조판을 함께 되돌린다.
- 빨라야 한다. 키 입력 한 번에 바뀐 쪽만 다시 그린다. 지연과 깜빡임은 버그로 다룬다.
- 실패한 명령은 롤백한다. 롤백마저 실패하면 세션을 잠그고 마지막 정상 결과를 유지한다.
- 개인 문서는 opt-in 로컬 검사에서만 쓴다. 본문을 로그나 저장소에 남기지 않는다.

## 현재 상태 (0.1.0)

- 앱: `DocumentGroup` 문서 앱(새 문서, 열기, 최근 문서, 저장, 다른 이름으로 저장, 버전), 쪽 썸네일, 쪽 맞춤으로 열기, 확대/축소, 프린트, PDF 내보내기.
- 창 구성(웹 한글과 같은 순서): 메뉴는 macOS 메뉴 막대(파일·편집·보기·입력·서식·쪽·표), 창 안에는 기본 도구 상자(가는 아이콘, 웹 한글 리본 순서에서 동작하는 것만), 서식 도구 상자, 사이드바(쪽 미리 보기) + 쪽, 상태 표시줄(쪽, 확대/축소). 도구 상자와 사이드바는 보기 메뉴에서 켜고 끈다. 메뉴 항목은 웹 한글 메뉴의 순서·묶음·이름·아이콘을 따르고, 도구 상자의 찾기·표·머리말·꼬리말은 웹처럼 이름 아래 ▾로 펼친다(표는 줄×칸 격자).
- 화면 갱신 비용: SwiftUI는 키 입력마다 바뀌지 않는 값(`EditingContext`: 선택 유무·표 안·쪽 수·실행 취소 가능, 캐럿 서식)만 관찰한다. 캔버스는 문서의 `presented`를 직접 받고, 썸네일은 입력이 0.4초 멈춘 뒤 바뀐다. 스크롤마다 바뀌는 쪽·확대율은 `ViewPosition`으로 분리했다. 글꼴 목록은 입력이 없는 별도 뷰라 한 번만 만든다.
- 메뉴 막대: 웹 한글의 상단 메뉴를 같은 순서로 macOS 메뉴 막대에 옮긴다. 동작하는 항목만 둔다.
- 서식 도구 상자: 되돌리기·다시 실행, 글꼴, 크기(입력·증감·목록), 진하게·기울임·밑줄(모양 13종)·취소선(모양 13종), 글자 색, 형광펜, 정렬 6종, 줄 간격(종류에 따라 % 또는 pt). 캐럿 위치의 서식을 보여 준다.
- 캐럿 서식: 선택 없이 고른 글자 서식은 그 자리에 이어 치는 글자(한글 조합 포함)에 적용되고, 입력과 같은 실행 취소 단위다.
- 글자 모양(⌘L): 글꼴, 기준 크기, 장평, 자간, 진하게·기울임·밑줄·취소선(모양), 외곽선, 그림자, 양각, 음각, 위·아래 첨자, 글자 색, 음영 색. 문단 모양(⌘T): 정렬, 왼쪽·오른쪽 여백, 첫 줄(보통·들여쓰기·내어쓰기), 줄 간격 4종, 문단 위·아래, 외톨이줄 보호·다음 문단과 함께·문단 보호·문단 앞에서 쪽 나눔. 둘 다 바꾼 항목만 적용한다(여러 서식이 섞인 선택을 덮어쓰지 않음).
- 형광펜은 글자 음영 색으로 칠한다(HWP의 형광펜은 문단 범위 태그라 편집 제약이 있어 보류).
- 편집 캔버스: PDFView 대신 쪽을 동기적으로 그리는 자체 뷰(바뀐 쪽과 커서가 같은 프레임에 바뀜, 페이드 없음). 클릭·드래그(자동 스크롤)·Shift 선택, 더블클릭 단어·트리플클릭 문단 선택, I-빔 포인터, 확대율과 상관없이 화면 1pt 굵기로 깜빡이는 커서, 커서를 화면 안에 유지, 문서 안 한글 조합,
  - 커서 이동은 엔진 조판 기준: 글자·단어(⌥←→)·줄 처음/끝(⌘←→)·위아래(열 유지, 쪽·셀 경계 넘김)·문단(⌥↑↓)·문서(⌘↑↓)·쪽(PageUp/Down), 각각 Shift로 선택 확장. 단어·줄 단위 삭제(⌥⌫, ⌘⌫). 화살표·줄 끝·문단 끝 이동, 삭제·문단 합치기, 여러 문단 선택 삭제·교체, 전체 선택(본문 또는 셀), 오려 두기·복사·붙이기, `UndoManager`와 연결한 실행 취소.
- 편집 엔진:
  - 명령: 본문·최상위 표 셀의 Replace(여러 문단 가능)/Split/MergePrevious, FormatText/FormatParagraphs, Break(쪽·단 나누기), InsertTable, EditTable(줄·칸 추가/삭제), SetPage(편집 용지), Undo/Redo(20단계), 조합용 amend.
  - 구조 명령의 보존 검사(테스트에서만): 표 삽입은 편집 문단 자리에 원래 컨트롤 + 표 하나만 생겨야 하고, 줄·칸 편집은 그 표만, 편집 용지는 그 구역의 용지 정의(구역 정의 컨트롤 사본 포함)만 바뀌어야 한다. DocInfo는 목록 끝에 덧붙는 것만 허용한다. 로컬 문서 47개에서 156회 실행해 거부 0(`structure_edits_on_corpus`, opt-in).
  - 조회: 찾기(본문·최상위 표 셀, 글상자·중첩 표·수식 제외), 편집 용지.
  - 안전장치: 문자소(grapheme) 경계 검증, 실패 시 롤백, 저장 전 재파싱 검증. 명령마다 바뀌어야 할 곳만 바뀌는지 보는 보존 검사는 문서 전체를 복사·비교하므로 테스트 빌드에서만 돈다(테스트와 opt-in 문서 묶음 검사로 명령 구현을 검증하고, 편집기는 키 입력마다 그 비용을 치르지 않는다). 쪽 배치 점검(layout audit)은 편집 경로에서 뺐다.
  - 조회: hit-test, 커서·선택 영역 좌표, 캐럿 위치 서식과 글꼴 대체 순서.
  - 저장: 검증을 거친 HWP/HWPX 저장.
- 렌더링: 편집마다 바뀐 쪽만 표시 목록(display list)으로 만들어 Core Graphics/Core Text로 바로 그린다. 표시 목록이 다루지 못하는 쪽만 PDF로 받는다. 4쪽 보고서에서 키 입력 한 번이 앱 왕복 24ms, 새 쪽 그리기 3ms다(이전 PDF 경로 45ms + 그리기, 처음 1.7–2.2초). 프린트·PDF 내보내기는 엔진이 전체 PDF를 새로 만든다.
- 앱과 엔진 경계: `hwp_edit_*` C ABI 하나. 문서 열기도 편집 세션으로 한다.
- 배포: SwiftPM, `make dist`로 서명·공증.

## 기능 목표 (웹 한글 메뉴 기준)

웹 한글(한컴오피스 Web v2) 편집 화면의 상단 메뉴 전체다. 저장해 둔 편집 화면의 메뉴 마크업에서 그대로 옮겼다.
macOS 메뉴 막대도 같은 순서로 둔다(파일·편집·보기·입력·서식·쪽·표, 검토·도구는 2차). 메뉴에는 동작하는 항목만 둔다.

단축키 원칙:
- 웹 한글의 Ctrl 단축키는 macOS 관례에 맞춘다.
- 글자 입력과 겹치는 ⌥ 단독 단축키는 ⌥⌘로 옮긴다.
- 한글 고유의 연속 단축키(Ctrl+N+T 같은 것)는 쓰지 않는다.

엔진 열의 함수는 rhwp `DocumentCore`에 이미 있는 API다. 상태가 빈 칸이면 아직 하지 않은 것이다.

## 단계

### 1. 편집 화면
- [x] 엔진: 선택 영역 사각형(`rhwp-layout.patch`로 `get_selection_rects_native` 공개), 저장 검증, 새 문서.
- [x] `HwpDocument`(`ReferenceFileDocument`): 편집과 이동을 제출 순서대로 하나씩 처리한다.
- [x] 편집 캔버스(PDFView 하위 클래스, `NSTextInputClient`).
- [ ] 실제 한글 입력기로 조합·확정·후보창 위치를 수동 검증한다(연속 음절 조합 버그는 수정·테스트함).
- [ ] 줄 끝 커서의 위치 선택(affinity): 줄바꿈된 줄의 끝은 현재 마지막 글자 앞에 선다.
- [x] 여러 문단에 걸친 선택의 삭제·교체. 사이 문단에 컨트롤이 있으면 거부한다.
- [ ] 자동 저장 정책: 저장 검증이 충분해질 때까지는 macOS 버전으로 이전 판을 보존한다.

### 2. 쪽 단위 렌더링
- [x] 엔진이 쪽마다 SVG 해시를 기억하고, 편집 위치 한 쪽 앞부터 다시 그리다가 편집 뒤 첫 같은 쪽에서 멈춘다. 쪽 수가 바뀌면 모든 쪽을 비교한다. 바뀐 쪽의 PDF만 돌려준다.
- [x] 앱은 `PDFDocument`의 쪽을 제자리에서 교체한다(문서 교체·깜빡임 없음). PDF 내보내기는 엔진이 전체를 새로 만든다.
- [x] rhwp 패치: PDF 변환이 글꼴 DB를 한 번만 만들고 글꼴 파일을 한 번만 매핑한다(쪽당 0.5초 → 50ms).
- [x] 앞 편집이 끝나기 전에 친 글자는 한 편집으로 묶는다.
- [x] svg2pdf 패치(`Vendor/svg2pdf.patch`): `<text>`마다 모든 글꼴을 복제하던 것과 변환마다 글꼴 파일 전체(10MB대)를 복사하던 것을 없앴다. rhwp 패치: 같은 글꼴 지정의 글꼴 선택을 기억한다. 쪽 PDF 56ms → 27ms.
- [x] (테스트 전용이 되기 전) 보존 검사는 바이트 덩어리(미리보기 그림, 원본 스트림)를 `==`로 비교하고 나머지만 `Debug` 문자열로 비교한다(키 입력당 약 7ms 절약).
- [x] 썸네일은 입력이 멈춘 뒤 백그라운드에서 그린다.
- [x] 화면 렌더러: 엔진(`editing/display.rs`)이 PDF로 바꿀 쪽 SVG를 그대로 읽어 이진 표시 목록으로 만들고, 앱(`PageDisplay.swift`)이 Core Graphics/Core Text로 그린다. SVG 의미를 그대로 따르므로 rhwp 레이아웃이 바뀌어도 화면과 PDF가 갈라지지 않는다.
  - 글꼴은 usvg와 같은 글꼴 DB·같은 질의·같은 대체 규칙으로 엔진이 고르고 글꼴 파일 경로를 넘긴다. 앱은 그 파일을 Core Text로 연다.
  - 다루는 SVG: `text`(textLength, 장평 transform, 굵기·기울임, 가운데 정렬), `rect`, `line`(점선), `path`, `circle`/`ellipse`, PNG/JPEG `image`, 중첩 `svg`, `g`(transform, 사각 clip). 그 밖의 요소·속성이 하나라도 있으면 그 쪽만 PDF로 그린다. 문서 25개 201쪽 중 199쪽이 표시 목록으로 그려진다(나머지는 화살표 marker).
  - 검증: `nativePagesMatchThePDF`가 표시 목록과 내보낸 PDF를 같은 크기로 래스터화해 비교한다. 위 문서들에서 다른 픽셀이 최대 0.02%.
  - 쪽 하나: SVG 4ms + 표시 목록 4ms(대부분 XML 파싱), 이진 47KB. 이전 SVG→PDF는 27ms(svg2pdf 패치 전 56ms)였다.
  - 시도 후 버린 것: rhwp Skia 직접 PDF(라틴 글꼴 대체가 달라짐, Skia 내려받기 필요), `NSImage` SVG 그리기(쪽당 120ms), PDF를 백그라운드에서 미리 그려 두기(표시 목록으로 대체).
- [ ] 남은 엔진 시간(약 20ms): 편집 쪽과 다음 쪽의 SVG(레이아웃 포함), 표시 목록의 XML 파싱. 보존 검사와 배치 점검은 편집 경로에서 뺐다(약 4ms). 다음 후보는 rhwp 렌더 트리에서 표시 목록을 바로 만드는 것(SVG 문자열과 XML 파싱 생략).
- [ ] 측정: 엔진 `HWP_BENCH=<문서> cargo test --release bench_typing -- --ignored --nocapture`, 앱 `HWP_BENCH=<문서> swift test -c release --filter benchHostedTyping`, 화면 확인 `HWP_SNAPSHOT_DIR=<폴더> swift test --filter snapshots`.

## 완료를 판단하는 검사

1. 생성한 HWP/HWPX에서 본문과 셀을 편집한 뒤에도 표·그림·편집하지 않은 문단이 그대로다(Rust 테스트).
2. 조합형 한글, ZWJ 이모지, 결합 문자에서 문자 경계가 깨지지 않는다.
3. Undo→Redo 후 텍스트·커서·쪽 수가 같다. 저장한 파일을 다시 열면 텍스트가 같다.
4. 렌더 실패를 주입하면 revision과 문서가 이전 상태 그대로다.
5. 확대율 50/100/200%와 쪽 경계에서 클릭한 위치와 커서가 맞는다.
6. 실제 macOS 한글 입력기로 조합→확정→Undo를 수동 확인한다. 확인하지 않았으면 지원 완료로 보고하지 않는다.
